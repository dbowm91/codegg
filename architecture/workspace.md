# Workspace

Workspace identity, the daemon-owned registry, the immutable execution context,
and the path policy that prevents tools from escaping project roots.

This module owns the lowest-level abstraction at which the daemon reasons about
"which project is the agent working on". It is UI-, server-, and plugin-free
and lives in `crates/codegg-core/src/workspace.rs`.

The typed identity foundation in `crates/codegg-core/src/identity.rs` keeps
logical project identity separate from this workspace locator. Each newly
bound canonical directory owns one logical project, and each new project has
one bound directory. Existing multi-directory bindings remain readable until
an operator rebinds them. Repository lineage is shared metadata and does not
merge clones or worktrees into one project.

## Why it exists

The single-daemon multi-project orchestration roadmap replaces the implicit
"current directory = project identity" model with an explicit, typed
workspace binding. Phase 2 makes every persisted session point at exactly
one `WorkspaceId` and propagates an immutable `ExecutionContext` through
every daemon-owned execution path.

## Key types

- `WorkspaceId` — typed `String` newtype identifying a registered workspace.
  Generated by the registry at registration time; never derived from path
  text so renames and host moves do not rename identifiers.
- `WorkspaceRecord` — persisted registry entry (`id`, `canonical_root`,
  `display_name`, `created_at`, `last_opened_at`, `archived_at`).
- `WorkspaceRegistry` — daemon-owned registry. Deduplicates canonical roots
  via `get_or_register`; requires an absolute root path and rejects
  nonexistent paths, file paths, and a symlink at the selected root.
  Hydrates from a `WorkspaceStore` and serves
  subsequent reads from an in-memory `DashMap` index.
- `WorkspaceStore` — persistence trait. Two implementations:
  `SqliteWorkspaceStore` (the production path) and
  `InMemoryWorkspaceStore` (tests).
- `ExecutionContext` — immutable, `Arc`-wrapped context carrying
  `workspace_id`, `workspace_root`, `session_id`, `allowed_read_roots`,
  `allowed_write_roots`, and a `CancellationToken`. Every daemon-owned
  execution path receives one of these through `TurnRunInput.execution`.

## Path policy

`ExecutionContext` exposes three helpers that should be the only way tools
and subsystems materialize a path:

- `resolve_relative_cwd(requested).await` — picks a working directory. `None` and
  empty strings resolve to the workspace root; relative paths join the
  workspace root and canonicalize; absolute paths must lie under an
  explicitly allowed root.
- `resolve_read_path(requested).await` — verifies and canonicalizes a read
  target. Existing paths canonicalize directly; paths that don't yet
  exist canonicalize the nearest existing ancestor and append the missing
  suffix. Relative paths must resolve under the workspace root.
- `resolve_write_path(requested).await` — same rules as read, plus the
  destination must lie under `allowed_write_roots`.

`PathPolicyError` distinguishes `OutsideWorkspace`, `OutsideAllowedRoots`,
`UnsupportedAlias`, `CanonicalizationFailed`, `EmptyPath`, and `ContainsNul`
so callers can render precise diagnostics.

## Session binding

The authoritative relation is:

```text
Session -> ProjectId + WorkspaceId -> canonical root

Project discovery may register an observed canonical root through the existing
workspace registry, but it does not activate a workspace service bundle. A
discovery observation is not an execution context; activation still requires
an explicit later project/workspace selection.
```

`SessionBinding` expresses the typed internal relation. Launch and local
picker opens share an idempotent ensure-bound flow: an unseen directory gets
a project named after its final path component, and reopening it returns the
existing binding. Selecting a project stores its canonical workspace root on
the client tab; `ExecutionContext` is resolved from that active tab and never
from daemon process cwd. `project_id` and
`directory` remain as compatibility projections in storage and DTOs; the
directory is a filesystem locator, not a project identity. New daemon code
reads `workspace_id`. `CoreDaemon::bind_runtime_for_session`
resolves a `session_id` to a `SessionRuntime` through `SessionStore` +
`WorkspaceRegistry`. `TurnSubmit`, `AgentSelect`, and `ModelSelect` reject
sessions whose `workspace_id` is `NULL` until rebound via
`CoreRequest::WorkspaceRegister`.

## Storage

Schema migration v22 (`crates/codegg-core/src/session/schema.rs:1125`) adds:

```sql
CREATE TABLE workspace (
    id TEXT PRIMARY KEY,
    canonical_root TEXT NOT NULL UNIQUE,
    display_name TEXT NOT NULL,
    time_created INTEGER NOT NULL,
    time_last_opened INTEGER NOT NULL,
    time_archived INTEGER
);

CREATE INDEX idx_workspace_archived ON workspace(time_archived);
CREATE INDEX idx_session_workspace_repair ON session(workspace_id);
```

The `session.workspace_id` column itself exists since the initial session
schema; v22 only creates the workspace registry table and an index to
accelerate workspace-based session lookups. Existing sessions are lazily
resolved on next access; their `directory` is canonicalized into a workspace
record. Sessions whose `directory` does not canonicalize to a real directory
remain unbound and are rejected at turn submission.

Schema migration v25 adds the canonical `workspace_project_binding` relation.
It binds one workspace to one logical `ProjectId`, an optional `RepositoryId`,
status, provenance, locator, and optimistic-concurrency revision. New bindings
are one directory to one project; historical projects with several bindings
remain readable and are graduated by the M4 rebind operation. Session bindings are stored separately in
`session_project_binding`; the legacy session columns remain projections.

`ProjectStorage::reconcile_workspace_path` probes only the explicitly
registered workspace and gathers Git evidence before opening a write
transaction. Missing or ambiguous lineage is retained as a diagnostic.
Repository lineage can be shared by separate project roots; it never selects
another root's project binding.

## Protocol

- DTO: `WorkspaceSnapshot { workspace_id, canonical_root, display_name, active_sessions }` in `crates/codegg-protocol/src/dto.rs:462`.
- Requests: `CoreRequest::WorkspaceRegister { root }`
  (LocalOwner/proven-local only: `opaque` + `project.configure`; no
  project locator, so team principals fail closed with
  `authorization_scope_required`),
  `CoreRequest::WorkspaceList { include_archived }` (global form is
  LocalOwner-only: `opaque` + `project.read`; canonical roots are never
  disclosed to team principals; project-filtered listing is future work),
  `CoreRequest::WorkspaceArchive { workspace_id }`,
  `CoreRequest::WorkspaceSnapshotRequest { workspace_id }`.
- Responses: `CoreResponse::WorkspaceList { workspaces }`,
  `CoreResponse::WorkspaceSnapshot { workspace }`.
- `SessionSnapshot` carries `workspace_id` (new) and `directory` (compat).
- `ServerCapabilities` advertises `workspace_registration` and
  `workspace_snapshots`.
- Authority: raw daemon-local registration/global enumeration is
  LocalOwner/proven-local deployment authority, not team bootstrap;
  `ProjectRegister` from a `workspace_id` locator is likewise
  LocalOwner-only until a durable workspace-ownership contract exists.
  Project-scoped workspace mutation under `project.configure`
  (`POST /api/workspace`) remains available; `POST /api/project` is
  `LocalOwnerOnly` compatibility.

## Propagation

- `TurnRunInput` (`src/agent/turn_runtime.rs:84`) carries
  `execution: Arc<ExecutionContext>`. The turn runtime uses
  `execution.workspace_root` for LSP context, Git context, project
  instructions, prompt loading, and tool registry construction.
- `ToolRegistryOptions` (`src/tool/mod.rs:276`) carries `workspace_root`.
  `build_session_tool_registry` (`src/tool/factory.rs`) anchors `RunStore`
  at `workspace_root/.codegg/runs/` and propagates `workspace_root` into
  tool options.
- Subagents receive the parent turn's `ExecutionContext` so that nested
  tool calls and `BashTool` invocations remain inside the same workspace.
- `BashTool` resolves cwd from the execution context first; relative
  `workdir` joins the workspace root, absolute paths must fall under an
  explicitly allowed root, and there is no process-cwd fallback for
  daemon-originated requests.

## Static guard

`scripts/check_daemon_cwd_usage.py` rejects **any** use of
`std::env::current_dir()`, a bare `current_dir(`, or
`std::env::set_current_dir(...)` inside daemon-owned execution surfaces:

- `src/tool/` (whole tree, including `bash/`, `terminal`, `formatter`,
  `tool_program`, `lsp`, `lsp_read`, `git_read`, `skill`, `backend`)
- `src/scheduler/` (whole tree)
- `src/core/`
- `src/agent/worker.rs`, `src/agent/turn_runtime.rs`
- Git execution services (`git_service.rs`, `git_mutations.rs`,
  `git_recovery.rs`)

`#[cfg(test)]` modules are skipped, and two files are exempt as pre-session
bootstrap: `src/main.rs` and `src/exec.rs`.

There is **no line-pattern allowlist**. The guard's predecessor had one, and
its patterns (`allowed_root: std::env::current_dir`, `let cwd = …`,
`std::env::current_dir().`) matched the production sites themselves — so it
exited 0 with every violation still in the tree, and could be cited as
evidence that the code was clean when it was not. Exemptions are now
whole-file with a written justification, because a pattern that matches a real
violation cannot be distinguished from one that does not.

Run `python3 scripts/check_daemon_cwd_usage.py --self-test` before trusting a
change to the guard: it feeds synthetic sources through the same detector and
fails if a planted violation is not reported. The negative case — injecting a
`std::env::current_dir()` read into `src/tool/read.rs` and confirming exit 1 —
is recorded in the W001 closure record.

`scripts/check_identity_path_usage.py` checks the canonical project-storage
module for path-derived `ProjectId` construction while leaving compatibility
projections untouched. Its `--fixture` mode verifies the negative case.

## Identity and locator separation

`WorkspaceId` is durable identity and `canonical_root` is execution locator
data. The daemon registry may hydrate or resolve an existing workspace, but
session load and turn submission do not register a workspace from a historical
directory. Directory compatibility is delegated to the canonical context
resolver and succeeds only for an existing unique project/workspace binding.
