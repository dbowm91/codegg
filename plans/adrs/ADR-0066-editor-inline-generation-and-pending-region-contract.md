## Context

The TUI editor is a real document surface: it opens a daemon-owned document,
paints it, edits it through `DocumentController::apply_local`, and answers an
LSP for it. What it cannot do is ask a model for a piece of code at the cursor.

The requested capability is a Zed-style inline insertion: a gesture opens a
small prompt, the operator types an instruction, the model's answer appears as a
differentiated region, and a menu at the cursor offers Approve, Deny and Edit.
The prompt field needs Helix NOR/INS semantics, multi-line input, its own
model and thinking level, and an Esc that clears and dismisses it.

Four repository facts make this a decision rather than a feature:

1. **The editor route has no chat session, and a turn needs one.**
   `TurnSubmit` carries a `session_id`; `SessionPromptSubmit` composes a
   turn from a durable session. The editor's document open establishes a
   project and workspace identity (`commands/editor.rs:195-230`) and nothing
   else. A turn started from the editor would hijack the session transcript and
   require a session the editor route does not have.

2. **The daemon already knows how to make a one-shot provider call.**
   `generate_title_via_provider` (`src/agent/title.rs:200-248`) exists
   precisely to avoid "scheduler admission and a result round-trip for a single
   short string", and `llm_summarize` (`src/context/compaction.rs:323-470`)
   is the same shape. Neither is exposed on the wire.

3. **The document authority forbids a second copy of the text.**
   ADR-0011 and `scripts/check_tui_editor_text_authority.py` keep the TUI free
   of a second document buffer and of any filesystem read. A generated
   insertion that is *not* yet document text therefore needs an explicitly
   bounded, non-document payload — and the renderer needs a way to draw it.

4. **The checked apply path refuses a dirty document.**
   `LspPreviewApply` carries patch text and `original_hash`, not a position,
   and the daemon applier rejects dirty managed LSP documents. The editor's
   buffer is dirty whenever the operator has typed, so the approval of an
   inline insertion cannot ride that path while the buffer is dirty; the
   editor's own `DocumentChange` path is the one that can carry an edit into
   an open document.

A fifth fact shapes the ergonomics rather than the architecture: the live
probe showed that the editor's `:` and `/` modal lines accept only an
unmodified key, so a terminal that reports the shifted spelling loses the
command line entirely and the character becomes document text. A new gesture
must therefore be spelled so its encoding is unambiguous.

## Decision drivers

- The operator's answer must reach the editor without a chat session and
  without touching the session transcript.
- The generated bytes must not become document text before the operator
  accepts them, because "Approve brings the generated text in" is the whole
  point of the review step.
- The daemon must remain the authority for the provider, the credential and
  the model; the frontend must not hold a second provider identity.
- The editor must keep exactly one text authority and one apply path.
- The per-request model and thinking level must be a per-request fact, not a
  change to the daemon's stored selection.
- A stale answer must never be applied to a document the operator has since
  changed.
- One keyboard axis, one spinner, one activity cadence, one comment budget.

## Considered options

### Option A — a pending region that is not document text

The model's answer is held in a bounded, editor-owned payload anchored at a
document byte offset. The renderer splices it into the line flow as a
differentiated region. The document's bytes are untouched, so the language
server, the file on disk and the undo history see nothing until the operator
approves. Approve constructs one insertion edit and submits it through
`submit_edit`; Deny drops the payload; Edit drops it and re-opens the prompt.

Benefits: the review step is honest, because nothing has been written anywhere;
Deny costs nothing and needs no undo entry; the language server is not asked to
track bytes that may be discarded; the write is a single normal edit with the
editor's existing undo, cursor and history semantics.

Costs: the renderer gains a layer that is not document text, and the visible
line computation must account for the region's height; the region's bytes live
in the frontend, so the text-authority guard needs one narrow, explicitly
bounded allowance; a region that is not document bytes must not participate in
the cursor's byte arithmetic, which is the subtlest part of the change.

Failure modes: a region that is not document text can drift from the document
if the document changes underneath it — which is why the region's anchor is
revalidated against the document revision before it is drawn or applied.

### Option B — the generated text enters the document immediately

The model's answer is inserted as an ordinary edit the moment it arrives, with
the pending state carried as a marker over a byte range. Approve keeps it, Deny
removes it with a second edit, Edit removes it and re-opens the prompt.

Benefits: the rendering is ordinary document text, so no new span layer and no
row-flow change; the region's identity is the document's own; the operator can
edit the generated code before accepting it.

Costs: the bytes are in the document before approval, which contradicts the
requested semantics; the language server receives a `didChange` for text that
may be discarded and another when it is; Deny is a second edit rather than a
dismissal; the document is dirty for an unapproved edit, which is precisely the
state the checked apply path refuses.

Failure modes: an operator who saves the file before deciding has written
unapproved generated code, and the deny path can conflict with the operator's
own edits in the meantime.

### Option C — ride an ordinary turn

The inline request is submitted as a normal turn in the session, and the answer
is extracted from the transcript.

Benefits: no new protocol, no new event, no new daemon request surface.

Costs: it requires a session the editor route does not have; it writes into
the session transcript, which is a different conversation; it inherits the
session's durable model selection, which is exactly the thing the operator
asked to be able to override; it consumes the turn budget and the tool loop for
a single short string; and it makes the inline answer indistinguishable from a
chat reply. This option is rejected.

### Option D — no pending region; insert on arrival

The answer is written into the document as soon as it arrives.

Benefits: the simplest possible contract; one edit, one path.

Costs: there is no review step at all, so the operator cannot deny or edit the
result; a wrong answer is already in the buffer and needs an undo. This
option is rejected because the requested behaviour is explicitly a review.

## Decision

**Option A is selected, together with a new one-shot generation request
surface.** This record was **accepted** on 2026-11-24; see the acceptance
record below. M001 of the roadmap implements this Decision and no other
option.

The decision has four parts.

### 1. A new one-shot request, not a turn

A new `CoreRequest` variant issues one bounded generation against a chosen
model. It carries the operator's instruction, the model, an optional reasoning
override, and the editor context the request needs. It does **not** carry or
create a session, does not run a tool loop, and does not admit a turn.

The daemon-side shape follows `generate_title_via_provider`: one
`ChatRequest` with `tools: None`, a bounded output budget, a bounded
timeout, and the resolved reasoning selection applied through the existing
`apply_reasoning_override` path so a per-request effort label reaches the
wire exactly as it does for a turn.

### 2. The response is a new event, not a turn event

The answer arrives as a new `CoreEvent` carrying the request id, the document
identity and revision it was asked against, the model, the effort label, and
the generated text. It is not a `TurnTextDelta`: that event is session- and
turn-scoped, and an inline answer belongs to neither.

### 3. The pending region is editor-owned and not document text

The generated bytes are held in a bounded editor payload anchored at a document
byte offset and a document revision. The payload is drawn as a differentiated
region; the document's bytes are unchanged. Approve submits exactly one
insertion edit through `submit_edit`; Deny drops the payload; Edit drops it and
re-opens the prompt with the previous instruction.

The payload is bounded by an explicit byte and line budget, and the
text-authority guard is amended with exactly one allowance for it — with a
self-test that proves the allowance is narrow.

### 4. The per-request model and thinking level are per-request facts

The request carries the operator's chosen model and an optional reasoning
override. The daemon resolves the effective selection as **explicit request
override > persisted principal preference > agent/model-profile default**,
which is the precedence ADR-0049 and the turn path already implement. A
request that names neither inherits the daemon's stored selection; a request
that names one overrides it for that request only and does not change the
stored selection.

This also settles the model: the one-shot request does not pass through turn
admission, so it is not bound by the session's durable model selection the way
`TurnSubmit.model` is. A request that names a model the operator cannot
reach is refused with a typed refusal naming the model, not silently
substituted.

## Acceptance record

**Accepted 2026-11-24** by the project maintainer, who chose **Option A** —
the pending region that is not document text — over the alternative in which
the generated answer enters the document immediately.

The acceptance covers the whole Decision:

1. the request is a **new one-shot `CoreRequest`**, not a session turn;
2. the answer arrives as a **new event**, not a turn event;
3. the pending region is **editor-owned and not document text** until the
   operator approves it;
4. the model and the thinking level are **per-request facts** that never
   change the daemon's stored selections.

Acceptance releases **M001** of
`plans/subsystems/tui-editor-inline-llm-assist-roadmap.md` for handoff and
authorizes nothing else. M002 remains blocked on M001's closure. The
acceptance does not amend ADR-0011, ADR-0021, ADR-0049 or ADR-0050, and it
does not promote this line's contract into `plans/000-`: the canonical
long-term specification is still silent on inline AI assistance, so the
contract remains **interim** under `plans/003-planning-process.md`.

Option B is **rejected**, not deferred: the generated answer does not enter
the document before the operator approves it. Option C (ride an ordinary
turn) and Option D (insert on arrival) are rejected for the reasons recorded
above. The rejected options are not re-opened by this acceptance; a later
change of mind is a **new** ADR that supersedes this one.

## Consequences

### Positive

- The review step is real: no generated byte is in the document, in the file or
  in the language server before the operator approves it.
- Deny and Edit cost nothing and leave no undo residue.
- The write is one ordinary edit, so the editor's undo, cursor and history
  semantics apply unchanged.
- The request is bounded and does not consume the session's turn budget, its
  tool loop, or its transcript.
- The per-request model and effort override finally has a path that is not the
  session's durable selection.

### Negative

- The renderer gains a layer that is not document text, and the visible-line
  computation must account for a spliced region. This is the largest technical
  risk in the line and is why the roadmap's first milestone carries it.
- The text-authority guard needs one narrow amendment, and the guard must prove
  the amendment is narrow.
- A pending payload is frontend state that a daemon restart does not restore.
  That is acceptable — an unapproved insertion has no durable meaning — but it
  must be stated rather than discovered.
- The canonical long-term specification is silent on inline AI assistance, so
  this line's contract is **interim** under `plans/003-planning-process.md`
  until an owner decision promotes it.

### Neutral or deferred

- The desktop frontend is not in scope. The request and event are frontend-
  neutral, so a later desktop surface can consume them.
- Multi-line generated regions, multi-file edits and a selection-replacing
  insertion are deferred.
- Streaming the answer into the region as it arrives is deferred; the first
  version shows a "generating" state and then the answer.

## Compatibility and migration

No storage change. No `STORAGE_LAYOUT_VERSION` bump.

The new request and event are additive. A frontend that does not know them is
unaffected. A daemon that does not know the request answers with an
`unsupported` response, which the frontend must render as an explicit refusal
rather than as silence.

The response event carries no field an older frontend interprets, so a
mixed-version daemon and frontend are safe.

The text-authority guard's amendment is a guard change, not a product change,
and its self-test must prove the amended guard still rejects a real second
document buffer.

## Security and reliability implications

- **Authorization.** The request runs in the daemon and uses the daemon's
  provider connection and credential. The frontend names a model; it never
  names a provider, an endpoint or a secret. A model the connection cannot
  serve is refused with a typed refusal.
- **Containment.** The editor's context is taken from the document the
  operator already has open, under the document's existing scope and
  containment. The request never carries a filesystem path.
- **Bounded work.** The request is bounded by an output budget, a timeout, an
  input-size budget and a context-size budget. A hostile or confused operator
  cannot make it unbounded.
- **Staleness.** The response carries the document revision it was asked
  against. A response for a superseded revision is not applied and not drawn;
  it is reported as stale.
- **Cancellation.** Closing the document, switching documents, or leaving the
  route cancels the outstanding request, and a late answer is dropped by the
  request-id and generation fence the editor already uses for completions.
- **No tool access.** The request runs with no tools. An inline insertion must
  not be able to read the filesystem or run commands.

## Verification

- The request surface is covered by daemon tests that assert the refusal
  matrix: an unknown model, a model the connection cannot serve, an
  unsupported reasoning label, an over-budget instruction and a timeout.
- The renderer change is covered by frame tests that assert the region's rows,
  its position relative to the document lines, the cursor's visibility inside
  it, and that a region which is not document text does not enter the
  document's byte arithmetic.
- The guard amendment is covered by the guard's own self-test, which must
  prove the amended guard still rejects a real second document buffer and
  rejects a payload over its budget.
- The stale-answer path is covered by a test that changes the document while a
  request is outstanding and asserts the answer is neither drawn nor applied.
- The end-to-end path is covered by a `tui-test` run against an isolated
  daemon, exercising the gesture, the prompt field's NOR/INS semantics, Esc,
  the generated region, and the three review verbs.

## Supersession

(native LSP read delivery), ADR-0021 (native editor completion and local
