  a **plugin catalogue** is its published listing. They are not the same
  thing, and this milestone introduces the second term.

## 1. Objective

The daemon's plugin registry becomes the authority for the plugin catalogue,
and the seven `/plugin-*` forms' catalogue `kind` is corrected to match
whoever owns each form's effect.

The milestone's deliverable is **one authority and a truthful
classification**: the daemon holds the registry, the frontends read the
daemon's catalogue rather than building their own, each form's `kind` says
who owns it, and `daemon_served` says the truth about it.

## 2. Why this milestone is ready

- **The daemon's plugin machinery exists and is complete.** The registry
  (`src/plugin/registry.rs:173`), the service
  (`src/plugin/service.rs:24`), the activation store
  (`src/plugin/activation.rs:142`), the install path
  (`src/plugin/install.rs:33`), the management API
  (`src/plugin/management.rs:280`) and the doctor
  (`src/plugin/management.rs:666`) are all present and tested.
- **The seven forms exist and are classified, wrongly.** All seven are
  `DaemonEffect` (`crates/codegg-core/src/command_catalog.rs:2633`, `:2651`,
  `:2669`, `:2687`, `:2705`, `:2723`, `:2741`) and the daemon serves none
  (`src/tui/command_route.rs:295`).
- **The classification is already generated.** The artifact
  (`.../artifacts/m007-d-command-classification.md:213-219`, `:593-599`)
  already records all seven as *"not served"* and *"misclassified"*, so the
  defect is visible rather than implicit.
- **The constraint is recorded and closed.** `plans/registry.md:1165` states
  the four mutating forms can only be daemon effects. The mechanism question
  is what remains, and it is an owner decision.

### 3.2 The daemon serves none of them

The daemon's command effect table is `EFFECT_TABLE` at
`src/core/daemon_commands.rs:1454`. It has **no** plugin row — a grep for
`"plugin` across that file returns zero matches — so `serves_form`
(`src/core/daemon_commands.rs:778-788`) is false for all seven. The route
falls back to `NotServed` (`src/tui/command_route.rs:153-161`), and the TUI
keeps its local arm. The repository asserts it:
`assert_eq!(route_for("plugin_install", ""), CommandRoute::NotServed);` at
`src/tui/command_route.rs:295`, under the comment *"The plugin family has no
daemon request surface."*

### 3.3 There is no daemon request, event or projection for the plugin catalogue

- **No `CoreRequest` variant mentions a plugin.** The only plugin-named
  protocol variant is the *event* `CoreEvent::PluginUiEffect`
  (`crates/codegg-protocol/src/core.rs:5006`), with its TUI counterpart
  `TuiMessage::PluginUiEffect` (`crates/codegg-protocol/src/tui.rs:88`).
- **The projection carries plugin surfaces, but the daemon does not fill
  them.** `plugin_panels` (`crates/codegg-protocol/src/tui.rs:263`) and
  `plugin_status_items` (`:266`) exist on the remote snapshot, and
  `source_plugin_id` (`:278`, `:293`) attributes a surface to its owner — but
  the TUI populates them from **its own local registry**
  (`src/tui/app/mod.rs:1459`, `:1482`, `:1519-1520`), not from a daemon
  projection. There is no daemon-published plugin status today.
- **No server route, no client request, no desktop command.** A grep for
  "plugin" across `src/server/` returns no matches; the client crate
  mentions plugins only in capability-flag defaults
  (`crates/codegg-client/src/lib.rs:127-134`); the desktop mentions a plugin
  only as a skill-source label (`apps/desktop/src/bridge-types.ts:382`).

### 3.4 Two registries, one durable file

`create_default_plugin_service` (`src/plugin/mod.rs:79`) constructs a **new**
`PluginRegistry` on every call (`:80`) and loads the durable activation store
at `:132-142`.

- **The daemon calls it per turn** — `src/core/daemon_turns.rs:909`, in the
  turn-execution path of `handle_turns_request` (`:274`) — and again on every
  asset refresh (`src/core/daemon_refresh.rs:547`).
- **The TUI calls it at startup** — `src/tui/app/mod.rs:1900-1907`, wrapping
  it in its own `PluginManager` (`:1905`).

Both read and write the same file, `<daemon root>/plugin-activation.json`
(`src/core/instance.rs:186-188`; root resolved at `src/core/instance.rs:98-101`).
The store's doc comment says *"The daemon singleton makes one process the
normal writer"* (`src/plugin/activation.rs:138-140`) — a singleton that does
not exist. The write is an atomic temp-file-plus-rename
(`src/plugin/activation.rs:239-255`), so the two writers do not corrupt each
other; they **diverge**, which is the worse failure.

### 3.6 The manifest does not cover the plugin writers today

`docs/writer-disposition.toml` declares **60 roots** (the guard reports
*"writer-disposition check ok: 60 declared roots, 18 writer tools, 36 writer
modules"*). The only plugin root is `src/plugin/runtime/process.rs`
(`docs/writer-disposition.toml:869-882`, a *process* root). There is **no**
entry for `src/plugin/activation.rs`, `src/plugin/install.rs` or
`src/plugin/management.rs`.

They are not detected either. The guard's `WRITER_SURFACE_DIRS`
(`scripts/check_writer_disposition.py:177-192`) does not include
`src/plugin`, and `WRITER_SURFACE_FILES` (`:195-201`) does not list them;
only `src/plugin/runtime/process.rs` is detected, via `PROCESS_SURFACE_FILES`
(`:212-224`). Measured directly against the guard's own detector: all three
files *would* be flagged (`has_effect_primitive` is true for
`src/plugin/activation.rs`, `src/plugin/install.rs` and
`src/plugin/management.rs`), and two of them would be false positives
(`src/plugin/registry.rs`, `src/plugin/service.rs`).

The manifest's vocabulary for a user-scoped root already exists and is
exercised: `src/core/instance.rs` is declared `surface = "daemon"`,
`scope = "non-checkout"`, `disposition = "out-of-contract"`,
`mediation = "none"`, with a named `owner`
(`docs/writer-disposition.toml:608-619`). A `non-checkout` scope **must**
carry `disposition = "out-of-contract"`
(`scripts/check_writer_disposition.py:637-640`), and every root must declare
a `mediation` (`:652-658`) and an `owner` (`:643-645`).

### 3.7 The frontend-action vocabulary is closed

`FrontendActionDisposition` has exactly two members, `NonMutating` and
`ProcessLaunching` (`crates/codegg-core/src/frontend_action.rs:24-29`), and
the guard admits exactly those two
(`scripts/check_frontend_action_set.py:68`). The `FrontendAction` enum has
**35** variants (`crates/codegg-core/src/frontend_action.rs:38-72`) and
`THE_FRONTEND_ACTION_SET` (`:170`) declares each one. The guard's closure
rule is: every frontend-effect catalogue form must be served by **exactly
one** declared action (`:331-345`), and a declared action may not serve a
daemon-effect form (`:326-330`).

## 4. Invariants that must not regress

1. **The catalogue's `kind` must be truthful.** A form's `kind` says who
   owns its effect, and the daemon publishes `daemon_served` per form
   (`src/core/daemon_commands.rs:881`). A form advertised as daemon-served
   and not served is the defect M007-G exists to remove.
2. **A frontend must never build a second plugin registry.** The daemon's
   registry is the authority; a frontend reads the daemon's catalogue.
   `plans/000-long-term-specification.md` §4.4 (`:95`) is the long-term
   rule.
3. **A mutating form is never a frontend action.** The disposition
   vocabulary is closed (`scripts/check_frontend_action_set.py:68`), and
   widening it is an owner decision recorded in ADR-0057, not a
   side effect of this plan.
4. **The four mutating forms write only to user-scoped roots.** No plugin
   form may write into a checkout, and the install/uninstall target stays
   fenced to the canonical plugins directory
   (`src/plugin/management.rs:562-575`).
5. **The activation file has exactly one writer.** Two processes writing it
   is the defect this milestone removes.
6. **No plugin-contributed command surface.** ADR-0052 defers it and this
   milestone does not revisit that (`plans/registry.md:1165`).
7. **The catalogue version is bumped** whenever the catalogue's contents
   change (`crates/codegg-core/src/command_catalog.rs:175-178`).

### 5.3 Decision points pending owner answer

**Five decisions are pending. Each work package that depends on one says so
at its own point, and is written so it can be executed once the decision
lands. No work package below silently picks one.** ADR-0057's `## Decision`
section is the authoritative statement of what is pending; this section
records the same list in the plan's own terms.

#### D1 — Does the daemon's plugin registry become a process-lifetime singleton?

*Statement:* whether `create_default_plugin_service`
(`src/plugin/mod.rs:79`) stops being called per turn
(`src/core/daemon_turns.rs:909`, `src/core/daemon_refresh.rs:547`) and
becomes one instance held by the daemon.

- **Option A — a process-lifetime singleton.** The daemon holds one
  `PluginService` for its lifetime; the TUI's `PluginManager`
  (`src/tui/app/mod.rs:1900-1907`) is retired in daemon mode. **Cost:** the
  daemon's construction site moves; the standalone (non-daemon) TUI keeps its
  own instance, so the "one authority" claim is scoped to daemon mode and
  must be said so precisely.
- **Option B — a fresh registry per turn, as today.** The daemon owns the
  catalogue only for the duration of a turn. **Cost:** the disagreement
  persists; a plugin installed between two turns is absent from the next
  turn's registry, and an uninstalled plugin survives into it. This option
  does not deliver the milestone's goal.
- **Option C — a singleton with a bounded rebuild.** The daemon holds one
  instance and rebuilds it on an explicit invalidation (an install, an
  uninstall, a refresh). **Cost:** an invalidation path is a new event; it
  must be triggered by the daemon's own mutations, or it will drift.

**Recommended: Option A**, with Option C's invalidation folded in — the
singleton is rebuilt when the daemon's own plugin mutations change it, not on
a timer.

**Consequence.** Work package **A** (the registry lifetime) is written
against A. D1 also gates work package **C** (the TUI's second instance) and
**E** (the activation file's single writer).

#### D2 — How does a frontend read the daemon's plugin catalogue?

*Statement:* the channel by which the read-only forms' data reaches a
frontend, given that a frontend action produces no `Run` and no
`CommandExecute` response.

- **Option A — a new published projection surface.** The daemon publishes
  the plugin catalogue as a projection, in the manner of ADR-0053. **Cost:**
  ADR-0053 has already decided the daemon's published projection surfaces
  (`plans/adrs/ADR-0053-daemon-published-projection-surfaces.md`), and
  ADR-0056 says *"No other accepted ADR is amended"* (`:85`). Adding a
  surface is therefore an owner decision about ADR-0053, not a silent
  extension.
- **Option B — a dedicated bounded request** (e.g. `CoreRequest::PluginList`).
  The frontend action fetches the catalogue and renders it. **Cost:** a
  request that is a read but not a `Run`; it must be bounded and typed, and
  it must not become a second way to mutate.
- **Option C — all seven forms are daemon effects.** The catalogue arrives
  as the `CommandExecute` response and no new channel is needed. **Cost:** a
  canonical `Run` per read-only invocation, which ADR-0056's spirit disfavours
  for reads that do not need one.

**Recommended: Option A**, because it is the shape ADR-0053 already
established for daemon-published state and it keeps a read off the `Run`
ledger. **Option C is the fallback** if the owner declines to extend
ADR-0053's surface set, and it is the option that needs no ADR-0053
decision at all.

**Consequence.** Work package **B** (the publication mechanism) is written
against A, with C as the documented fallback. D2 gates work package **D**
(the catalogue's `kind` corrections), because a frontend action is only
correct if it has something to read.

#### D3 — Which capability authorises the four mutating forms?

*Statement:* the capability that gates `/plugin-enable`, `/plugin-disable`,
`/plugin-remove` and `/plugin-install`.

- **Option A — the generic `command.execute`.** `CommandCapability` has
  exactly one member (`crates/codegg-core/src/command_catalog.rs`), so this
  is the zero-new-surface choice. **Cost:** installing code is a far
  stronger authority than running a command, and ADR-0056's precedent for
  the LSP controls was a *narrow* capability granted to named roles and not
  inferred from `file.read` or `command.execute`
  (`plans/adrs/ADR-0056-...:38-40`).
- **Option B — a narrow `plugin.manage`,** by direct analogy with
  `lsp.control` (`crates/codegg-core/src/team.rs:294`, the 22-member role
  capability vocabulary, which has **no** plugin capability). **Cost:** a new
  capability, a role-grant table change, and a policy decision about who may
  install code.

**Recommended: Option B.** The four forms install, remove and enable code
that the agent then runs; `command.execute` is too coarse an authority for
that, and ADR-0056 set the precedent that such controls get their own
explicitly-granted capability.

**Consequence.** Work package **F** (the daemon requests and their
authority) is gated on D3. D3 also decides whether the catalogue's
`capability` for the four forms changes from `command.execute`.

#### D4 — Who writes `plugin-activation.json`?

*Statement:* the single writer of `<daemon root>/plugin-activation.json`
(`src/core/instance.rs:186-188`), reached today by both the daemon's
per-turn service and the TUI's manager.

- **Option A — the daemon is the sole writer.** The TUI's activation writes
  become daemon requests. **Cost:** the standalone TUI, with no daemon,
  cannot enable or disable a plugin; it must say so honestly.
- **Option B — the file is split** into a daemon-global scope and a
  frontend-local scope. **Cost:** two activation semantics, and the
  resolution rules between them are a new policy.
- **Option C — an inter-process lock.** The store takes a file lock. **Cost:**
  lock ordering, stale locks, and a lock that a crashed process leaves
  behind.

**Recommended: Option A**, scoped honestly: the daemon is the sole writer
when a daemon is running; the standalone TUI keeps its own writer and says
so. Option C is the only one that preserves the current behaviour exactly,
and it is the most machinery.

**Consequence.** Work package **E** is gated on D4, and D4 interacts with
D1: a daemon singleton (D1 Option A) is what makes A possible.

#### D5 — Does the desktop gain plugin commands in this milestone?

*Statement:* whether the desktop's palette gains the seven forms in M007-G.

- **Option A — yes, and automatically.** The desktop's palette consumes the
  daemon's catalogue, so a form the daemon serves becomes dispatchable there
  with no new desktop command surface. The read-only frontend actions need
  the daemon's published catalogue to render, which is D2.
- **Option B — the desktop stays out of it.** The milestone is TUI-only and
  the desktop's plugin surface is a later milestone.

**Recommended: Option A.** The desktop's palette already consumes the same
catalogue (M007-D's record), so Option A costs the desktop nothing beyond
rendering the published catalogue.

**Consequence.** Work package **G** (the desktop) is gated on D2 and D5.

## 6. Required production changes

### 6.1 The mechanism, per form

and is therefore conditional. The "daemon serves it?" column is the current

**What the effect table must gain and lose.** The daemon's `EFFECT_TABLE`
(`src/core/daemon_commands.rs:1454`) must **gain** a row for each form that
becomes a daemon effect (four rows under the recommended split), and **lose
nothing** — the seven have no rows today, so a frontend-effect form has no
row to remove. If the owner takes D2 Option C (all seven daemon effects), the
table gains seven rows and the catalogue's `kind` stays `DaemonEffect` for all
seven, and the roadmap row's phrase *"the seven `/plugin-*` forms' catalog
`kind` is corrected"* no longer describes the work.

**What a `kind` correction requires, mechanically.**

- `crates/codegg-core/src/command_catalog.rs` — the form's `kind` becomes
  `CommandKind::FrontendEffect`, and the command's `capability` becomes
  `None` (a wholly-frontend command may name no daemon capability —
  `scripts/check_command_catalog_ownership.py:456-468`).
- `crates/codegg-core/src/frontend_action.rs` — a **new `FrontendAction`
  variant** and a **declaration** in `THE_FRONTEND_ACTION_SET` (`:170`) with
  its `disposition` and its `(command_id, form)` pair. The guard's closure
  rule is exact: every frontend-effect form must be served by exactly one
  declared action (`scripts/check_frontend_action_set.py:331-345`), and every
  enum variant must be declared (`:294-299`).
- `crates/codegg-core/src/command_catalog.rs` — the **catalogue version is
  bumped** (currently `version: 2` at `:242`).
- The TUI's arms for the three forms change from a local `PluginManager`

- The desktop's palette needs no new command surface; it dispatches the

### 6.2 The writer-disposition entries the mutating forms need

The schema a new root must satisfy, from `scripts/check_writer_disposition.py`:

- **Required keys:** `id`, `path`, `surface`, `scope`, `disposition`,
  `mediation`, `owner`. `locator` and `lifetime` are carried by the
  convention but are not enforced.
- **`surface`** — one of `model-tool`, `direct-tool`, `daemon`, `http`,
  `project-state`, `process`, `external` (`:85-92`).
- **`scope`** — one of `checkout-writer`, `non-checkout`, `read-only`,
  `external` (`:76-81`). A `non-checkout` root **must** have
  `disposition = "out-of-contract"` (`:637-640`); a `read-only` root must
  have `disposition = "allowed-read"` (`:634-636`).
- **`disposition`** — one of `allowed-read`, `fenced-native`,
  `denied-process`, `fenced-or-denied`, `mediated-gate`, `namespaced-state`,
  `shared-sidecar`, `compatibility-store`, `new-root-only`, `unsupported`,
  `out-of-contract` (`:57-71`).
- **`mediation`** — one of `process-gate`, `writer-fence`, `checkout-gate`,
  `none` (`:74-79`). Every root must declare one (`:652-658`). `none` is a
  **claim**: the root's disposition must say why no checkout mediation
  applies (`:70-72`).
- **`owner`** — a named final effect owner; a root without one fails
  (`:643-645`).
- `mediation_site` and `mediation_markers` are required **only** for a
  `checkout-gate` root (`:679-712`); a root whose mediation is `none` must
  not declare them (`:713-717`).

**`PROCESS_SURFACE_FILES`** (`scripts/check_writer_disposition.py:212-224`)
is the list of files the guard treats as **process-launching** writer roots —
the launcher owns what the child writes, so the root is declared and denied
rather than inferred. Its ten entries are `src/managed_process.rs`,
`src/scheduler/executors.rs`, `src/python_script/executor.rs`,
`src/interactive_process.rs`, `src/mcp/local.rs`, `crates/egglsp/src/launch.rs`,
`src/plugin/runtime/process.rs`, `src/hooks/mod.rs`, `src/tool/formatter.rs`
and `src/shell/runtime.rs`. **A new launcher is a deliberate addition to
this list *and* to the manifest — never a silent omission.** The plugin
*management* surfaces are not launchers and do not belong here; the plugin
*runtime* already is.

**The guard's detection must be widened, deliberately.** `src/plugin` is not
in `WRITER_SURFACE_DIRS` (`:177-192`), so `src/plugin/activation.rs`,
`src/plugin/install.rs` and `src/plugin/management.rs` are currently
invisible to the guard even though all three perform filesystem effects.
Adding `src/plugin` to that list is a **guard edit**, and it is an
implementation decision this milestone owns because it is the milestone that
makes the daemon own these effects. The detector's `has_effect_primitive`
returns true for all three and false for `src/plugin/registry.rs` and
`src/plugin/service.rs`, so the widened sweep names exactly three new roots.

### 6.3 The TUI's arms

The seven arms live at `src/tui/app/mod.rs:8719`, `:8916`, `:8926`, `:8936`,

### 6.4 Protocol

If D2 Option A is taken, a projection surface is added under ADR-0053's
rules; if D2 Option B, a bounded request variant is added. Both are additive
and typed. `daemon_served` and `action` are already `#[serde(default)]` on
`CommandFormDto` (`crates/codegg-protocol/src/core.rs:1224-1250`), so an
older client decodes the changed catalogue without a protocol break.

### 6.5 Security

The four mutating forms change what the machine loads and runs. Their
capability (D3) must be explicit and narrowly granted, and the canonical
`Run` must name the plugin identity and the effect. The install copy stays
fenced to the canonical plugins directory, and no plugin form may write into
a checkout.

## 8. Failure, cancellation, restart, contention semantics

- **The daemon's registry cannot be built.** Today's behaviour degrades
  cleanly: *"plugin activation state is unavailable; plugins disabled"*
  (`src/plugin/mod.rs:139`), and `create_default_plugin_service` returns
  `None`. That must not change.
- **A plugin is installed while a turn is running.** Under D1 Option A the
  singleton sees it at the next invalidation; under today's per-turn
  construction it does not. The behaviour must be stated, not accidental.
- **Two frontends mutate the plugin set concurrently.** The canonical `Run`
  serialises the effect through the daemon, and the activation store's
  temp-file-plus-rename (`src/plugin/activation.rs:250-254`) makes the
  durable write atomic. Under D4 Option A the daemon is the only writer and
  the race disappears.
- **A stale catalogue.** A `CommandExecute` carrying an old catalogue
  version is refused with `StaleCatalog`, and the frontend refetches
  (`crates/codegg-protocol/src/core.rs:1288-1296`).

## 9. Compatibility and migration

The catalogue version is bumped, so an in-flight `CommandExecute` carrying the
old version is refused rather than executed against a changed classification.
An older client decodes the changed catalogue without a protocol break
(`daemon_served` and `action` are `#[serde(default)]`,
`crates/codegg-protocol/src/core.rs:1238-1250`). No storage migration is
proposed: `plugin-activation.json`'s schema is unchanged
(`src/plugin/activation.rs`), and the plugin install directory's layout is
unchanged. The TUI's standalone mode is the only behavioural compatibility
surface, and D1/D4 decide what it does.
