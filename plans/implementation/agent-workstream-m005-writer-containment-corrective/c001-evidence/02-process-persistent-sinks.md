## Sink: `bash` — model-originated finite command (foreground, supervised)

- **Final effect owner**: `ManagedProcessService::run` — the single managed-process owner for finite argv work (`src/tool/bash/process.rs:461`, `src/managed_process.rs:802`). The `bash` tool is a caller, not the owner.
- **Checkout locator**: `canonical_workdir`, resolved from the tool's `allowed_paths` (`src/tool/bash.rs:570-607`), falling back to the tool's `workspace_root` (`src/tool/bash.rs:647-649`). A managed dispatch with no canonical workdir is refused, not defaulted to the daemon cwd (`src/tool/bash/process.rs:373-381`).
- **Authority path**: `request.execution_authorization = authorization` (`src/tool/bash/process.rs:428`) carries the broker's accepted-invocation authorization into the launch. Sandbox is decided from the host backend at one place (`src/tool/bash/process.rs:387-410`): `Unconstrained` → `SandboxRequest::Disabled`, `Contained` → `SandboxRequest::Required`, `Unavailable` → the command is **refused** (`src/tool/bash/process.rs:405-409`).
- **Lifetime (incl. detach/descendant question)**: The child is made a session leader via `setsid()` in a `pre_exec` hook (`src/managed_process.rs:1760-1772`, call site `src/managed_process.rs:793`). Cleanup is a **process-group** signal: `SIGTERM` to the group, then unconditional `SIGKILL` to the group (`src/managed_process.rs:1795-1806`, `src/managed_process.rs:1813-1853`). **This is not filesystem containment and it is not proven descendant-tree quiescence**: the source itself states that a descendant that calls `setsid` escapes the group kill and can keep the pipe open indefinitely (`src/managed_process.rs:1666-1669`). `kill_on_drop(true)` is direct-child only (`src/managed_process.rs:777`). On **Windows only**, the child is assigned to a Job Object created with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`src/managed_process.rs:799-800`, `src/managed_process/windows.rs:849-869`, flag set at `src/managed_process/windows.rs:856`), and termination calls `job.terminate(1)` (`src/managed_process.rs:1860-1868`) — that is a real tree kill, but it is a Windows-only mechanism and it bounds *lifetime*, not *write authority*.
- **Reachable callers**: tool name `bash` (`src/tool/bash.rs:395-397`), category `ToolCategory::ShellExec` (`src/tool/bash.rs:442-444`). Reached through the `ToolBroker`, the daemon turn loop, and the CLI/TUI frontends. `ShellExec` is not permission-free (`src/tool/mod.rs:147-152`).
- **Existing coordination (and its limits)**: Scheduler admission gates process slots and CPU/IO/memory (`src/scheduler/admission.rs:164-198`) and the executor must hold a live permit (`src/scheduler/executor.rs:191-195`). **Limits**: (a) `JobKind::Shell` and `JobKind::ManagedProcess` carry **no** exclusivity key (`crates/codegg-core/src/jobs/mod.rs:755-762`), so a shell writer never contends with a build or with another shell for the same checkout; (b) `exclusive:workspace-mutation` is held only by `JobKind::Build` and `JobKind::Format` (`crates/codegg-core/src/jobs/mod.rs:723-730`, `crates/codegg-core/src/jobs/mod.rs:739-746`) and `exclusive:worktree-mutation` only by `JobKind::GitMutation` (`crates/codegg-core/src/jobs/mod.rs:779-786`); (c) key matching is **bare-name exact match** (`src/scheduler/admission.rs:201-211`), so `workspace-mutation` and `worktree-mutation` never conflict with each other; (d) the resource profile is derived from the job kind at the single submission boundary (`src/scheduler/submission.rs:467-470`); (e) the admission controller is a single in-process controller whose `held_keys` map is global, not per-checkout, and the permit is released when the permit guard drops (`src/scheduler/admission.rs:272-289`) — it tracks a *process*, never a *file*.
- **Adversarial bypass example**: `bash` runs `sh -c 'setsid sh -c "while :; do printf x >> $PWD/shared.txt; done" &'`. The inner `setsid` puts the writer in a new session, outside the group the daemon signals (`src/managed_process.rs:1666-1669` documents exactly this escape). The tool call returns; the writer keeps appending to the shared checkout indefinitely, with no permit held and no `workspace-mutation` key ever taken.
- **Preliminary disposition**: **denied-process**.
- **Evidence**: `src/tool/bash.rs:395-397`, `src/tool/bash.rs:442-444`, `src/tool/bash.rs:570-607`, `src/tool/bash.rs:647-649`, `src/tool/bash/process.rs:373-381`, `src/tool/bash/process.rs:387-410`, `src/tool/bash/process.rs:417-461`, `src/managed_process.rs:406-423`, `src/managed_process.rs:771-802`, `src/managed_process.rs:1662-1683`, `src/managed_process.rs:1760-1772`, `src/managed_process.rs:1787-1853`, `src/managed_process/windows.rs:849-869`, `crates/codegg-core/src/jobs/mod.rs:755-762`, `src/scheduler/admission.rs:199-211`, `src/scheduler/submission.rs:467-470`.

## Sink: `bash` background / scheduler `JobKind::Shell` — durable job that outlives the request

- **Final effect owner**: `ManagedArgvExecutor` (`src/scheduler/executors.rs:241-255`, `src/scheduler/executors.rs:282-340`), which launches through `ManagedProcessService`.
- **Checkout locator**: the **durable job payload's `cwd` string** (`src/scheduler/executors.rs:321-326`), not `JobExecutionContext.workspace_root` — even though the context field's own doc says executors "must use this instead of consulting process-global CWD" (`src/scheduler/executor.rs:150-152`). A payload with no cwd is a hard failure, not a fallback (`src/scheduler/executors.rs:328-340`). The payload cwd is written by the submitter from `canonical_workdir` (`src/tool/bash/process.rs:1594-1598`).
- **Authority path**: durable acceptance through `JobSubmissionService` + the job-notification service, requiring a host-originated session context (`src/tool/bash/process.rs:1497-1506`, `src/tool/bash/process.rs:1462-1464`), an owner principal carried on the submission (`src/tool/bash/process.rs:1470-1481`), and a workspace root resolved through `workspace_id_for_root` (`src/tool/bash/process.rs:1507-1510`).
- **Lifetime (incl. detach/descendant question)**: The job is durable and runs **after** the tool call returns — by construction the process outlives the request. Its own process lifetime is the same setsid + process-group scheme as above (`src/managed_process.rs:1760-1772`, `src/managed_process.rs:1787-1853`), with the same documented `setsid` escape (`src/managed_process.rs:1666-1669`). The permit guard is held by the executor and dropped only after the executor has stopped (`src/scheduler/executor.rs:140-144`).
- **Reachable callers**: `bash` with background disposition (`src/tool/bash.rs:701-720` → `src/tool/bash/process.rs:1487-1516`); also the `test`/active-routing background variants (`src/tool/bash/process.rs:1631-1652`).
- **Existing coordination (and its limits)**: Scheduler queue + admission (`src/scheduler/admission.rs:164-198`), durable submission key and idempotency (`src/tool/bash/process.rs:1511-1518`). **Limits**: `JobKind::Shell` has no exclusivity key (`crates/codegg-core/src/jobs/mod.rs:755-762`), so a durable background shell and a durable build can write the same checkout concurrently with no contention recorded.
- **Adversarial bypass example**: submit a background `bash` job that writes `shared.txt` in a loop, then let the daemon restart. The job is durable and re-admitted from the store; the process it launches again escapes the group with `setsid` and keeps writing with no live permit and no exclusivity key.
- **Preliminary disposition**: **denied-process**.
- **Evidence**: `src/scheduler/executors.rs:241-255`, `src/scheduler/executors.rs:282-340`, `src/scheduler/executor.rs:140-152`, `src/tool/bash.rs:701-720`, `src/tool/bash/process.rs:1462-1518`, `src/tool/bash/process.rs:1594-1598`, `crates/codegg-core/src/jobs/mod.rs:755-762`.

## Sink: PTY attach / interactive process (long-lived)

- **Final effect owner**: `InteractiveProcessService` — declared the "single production owner of PTY-backed child lifecycle" (`src/interactive_process.rs:1-7`), with the daemon-side attach/authority layer in `InteractiveProcessProtocol` (`src/interactive_process_attach.rs:1-43`).
- **Checkout locator**: `ExecutionContext::resolve_relative_cwd(spec.cwd)` (`src/interactive_process.rs:614`), where `ExecutionContext` carries the canonical `workspace_root` (`crates/codegg-core/src/workspace.rs:655-665`, `crates/codegg-core/src/workspace.rs:725-739`).
- **Authority path**: Scheduler admission **before** any PTY or child is created (`src/interactive_process.rs:33-40`, `src/interactive_process.rs:623-624`); the attach layer derives authority from transport evidence, not caller-supplied identity (`src/interactive_process_attach.rs:18-33`), and `create` validates client id and DTO before spawning (`src/interactive_process_attach.rs:592-609`). **There is no filesystem sandbox on this path** — the child is launched with `env_clear()` and no `SandboxRequest` (`src/interactive_process.rs:1261-1298`).
- **Lifetime (incl. detach/descendant question)**: Long-lived by design and explicitly **not** request-scoped: "Detach and disconnect only drop attachments. The process follows the M001 owner/idle policy: it keeps running until explicit terminate, natural exit, remove, or daemon shutdown" (`src/interactive_process_attach.rs:33-35`). Termination is a **process-group** `SIGTERM` escalating to `SIGKILL` (`src/interactive_process.rs:891`, `src/interactive_process.rs:894`; drop path at `src/interactive_process.rs:955-966`). The child is a session leader via `setsid()` + `TIOCSCTTY` (`src/interactive_process.rs:1283-1297`). **A descendant that calls `setsid` escapes the group signal exactly as in the managed-process path** — this sink inherits the same unproven descendant quiescence.
- **Reachable callers**: TUI interactive-terminal command (`src/tui/commands/interactive_terminal.rs:2762`, `src/tui/commands/interactive_terminal.rs:3012`), daemon wiring (`src/core/daemon_construct.rs:588`, `src/core/daemon.rs:64`). **This is a human surface**: "No model-facing tool is registered here" (`src/interactive_process.rs:22-23`).
- **Existing coordination (and its limits)**: One scheduler process slot per PTY (`src/interactive_process.rs:503`, `src/interactive_process.rs:623-624`). **Limits**: process-slot admission bounds *concurrency*, never *lifetime* and never *which files* the PTY may write; there is no filesystem containment on this path.
- **Adversarial bypass example**: a human opens the TUI interactive terminal and runs `setsid sh -c 'while :; do printf x >> $PWD/shared.txt; done' &`. Detach leaves the process running (`src/interactive_process_attach.rs:33-35`), the group kill cannot reach the `setsid` descendant, and the PTY has no filesystem sandbox, so it keeps writing to the shared checkout indefinitely.
- **Preliminary disposition**: **denied-process** (C005 work package C: "No PTY lifetime restriction by simply releasing the permit on the first tool return; refuse in v1").
- **Evidence**: `src/interactive_process.rs:1-7`, `src/interactive_process.rs:22-25`, `src/interactive_process.rs:33-40`, `src/interactive_process.rs:503`, `src/interactive_process.rs:589-624`, `src/interactive_process.rs:857-902`, `src/interactive_process.rs:955-966`, `src/interactive_process.rs:1261-1298`, `src/interactive_process_attach.rs:1-43`, `src/interactive_process_attach.rs:592-609`, `crates/codegg-core/src/workspace.rs:655-665`, `crates/codegg-core/src/workspace.rs:725-739`.

- **Checkout locator**: **none.** `LocalClient::new` spawns with `Command::new(&self.command)` and sets `kill_on_drop(true)` but **no `current_dir`** — the child therefore inherits the daemon process's working directory. A grep for `current_dir` across the whole of `src/mcp/` returns **no match** (exit 1).

- **Lifetime (incl. detach/descendant question)**: Persistent by construction — the child is held for the life of the `LocalClient`. Shutdown is `child.kill().await` then `child.wait().await` (`src/mcp/local.rs:507-520`, kill at `:516`), and `Drop` calls `start_kill()` (`src/mcp/local.rs:724-728`). **Both are direct-child operations.** There is no `setsid`, no process group, and no descendant tracking anywhere in `src/mcp/local.rs` — a grep for `setsid|process_group|setpgid|pre_exec` across `src/` and `crates/` returns no hit in this file.

- **Existing coordination (and its limits)**: MCP server configuration and a per-call timeout (`src/mcp/local.rs:99-104`). **Limits**: no scheduler admission, no exclusivity key, no sandbox, and no write-authority locator at all. A local MCP server inherits the daemon's cwd and runs with the daemon user's full filesystem authority.
- **Adversarial bypass example**: an operator-configured local MCP server that, on `initialize`, forks a child that appends to the shared checkout; the parent's `child.kill()` (`src/mcp/local.rs:516`) kills only the parent, the grandchild survives, and because the child inherited the daemon cwd it writes wherever the daemon was launched.
- **Preliminary disposition**: **denied-process**.
- **Evidence**: `src/mcp/local.rs:99-104`, `src/mcp/local.rs:507-520`, `src/mcp/local.rs:613`, `src/mcp/local.rs:724-728`, `src/mcp/mod.rs:283-318`, `src/mcp/mod.rs:322-336`, `src/mcp/mod.rs:746-763`, `src/mcp/mod.rs:193-234`, `src/search_backend/bootstrap.rs:206-213`.

## Sink: LSP server child (persistent)

- **Final effect owner**: `egglsp`'s authoritative runtime — `crates/egglsp/src/runtime.rs` owns the child and reaps it; `launch::spawn_server*` creates it (`crates/egglsp/src/launch.rs:78-100`, `crates/egglsp/src/launch.rs:102-131`).

- **Lifetime (incl. detach/descendant question)**: Persistent across the daemon's life. `kill_on_drop(true)` and `env_clear()` are set (`crates/egglsp/src/launch.rs:114-115`), and the force-kill path is `child.start_kill()` (`crates/egglsp/src/runtime.rs:263`) followed by `child.wait()` (`crates/egglsp/src/runtime.rs:270`, `:277`, `:281`). **Direct child only** — a grep for `setsid|process_group|setpgid|pre_exec` across the whole of `crates/egglsp/src/` returns **no match** (exit 1), so there is no process group, no session, and no descendant tracking. `launch::terminate` is likewise `process.child.kill()` (`crates/egglsp/src/launch.rs:209-213`).
- **Reachable callers**: daemon-owned `LspService` (`src/core/daemon_lsp.rs:36`, `src/core/daemon_lsp.rs:167-168`), turn runtime (`src/agent/turn_runtime.rs:116`, `src/agent/turn_runtime.rs:1317`), LSP read/preview-apply tools (`src/tool/lsp.rs:2801-2803` category `ReadOnly`; `src/tool/lsp_preview_apply.rs:310-312` category `Mutating`).

The write lands in the shared checkout with no scheduler record, no exclusivity key, and no sandbox; the server keeps running after the request that started it.
- **Preliminary disposition**: **denied-process** (as a persistent process writer). The *LSP-mediated edit application* itself is a native writer and belongs to the fenced-native-candidate family, not here.

## Sink: process-backed plugin runtime

- **Final effect owner**: `ProcessRuntime` in `src/plugin/runtime/process.rs`; it launches through `ManagedProcessService::run` (`src/plugin/runtime/process.rs:149-150`), so the managed-process lifetime rules apply.
- **Checkout locator**: `self.spec.cwd` if set, otherwise **`std::env::current_dir()`** (`src/plugin/runtime/process.rs:95-101`). `PluginRuntimeSpec::Process` always constructs with `cwd: None` (`src/plugin/runtime/process.rs:82`), so the process-global CWD is the normal case.
- **Authority path**: plugin trust/policy class — `PluginRuntimeSpec::Process` is allowed only when `allow_process_lifecycle_hooks` is set (`src/plugin/policy.rs:68-75`), and `PluginTrustClass::LocalProcess` likewise (`src/plugin/policy.rs:78-85`). Runtime construction happens in the plugin service (`src/plugin/service.rs:334-339`, `src/plugin/service.rs:476-480`). The availability doctor only checks that the executable exists on PATH (`src/plugin/management.rs:1043-1066`, `command_exists` at `:1083-1089`). The request is built with `ManagedProcessRequest::new`, hence `sandbox: Disabled` and `execution_authorization: None` (`src/plugin/runtime/process.rs:128-135`, `src/managed_process.rs:406-423`).
- **Lifetime (incl. detach/descendant question)**: Bounded by the managed-process scheme (setsid + group TERM/KILL) with the same documented `setsid` descendant escape (`src/managed_process.rs:1666-1669`). The plugin child is not itself persistent — but a descendant it spawns is.
- **Reachable callers**: the plugin tool adapter, whose name is the plugin's canonical name and whose category is forced to `Mutating` ("Plugin hints never lower host permission requirements", `src/tool/plugin.rs:31-33`, `src/tool/plugin.rs:43-46`).
- **Existing coordination (and its limits)**: plugin trust class + lifecycle policy; a timeout (`src/plugin/runtime/process.rs:93`, `src/plugin/runtime/process.rs:137`). **Limits**: no scheduler admission, no exclusivity key, no sandbox, and a checkout locator that is the daemon's process CWD.
- **Adversarial bypass example**: an installed process plugin whose command is `sh` with args `-c 'setsid sh -c "printf x >> $PWD/shared.txt" &'`. The plugin's cwd is the daemon's launch directory, the sandbox is disabled, and the `setsid` descendant keeps writing after the plugin invocation returns.
- **Preliminary disposition**: **denied-process**.
- **Evidence**: `src/plugin/runtime/process.rs:82`, `src/plugin/runtime/process.rs:95-101`, `src/plugin/runtime/process.rs:128-150`, `src/plugin/policy.rs:68-85`, `src/plugin/service.rs:334-339`, `src/plugin/management.rs:1043-1066`, `src/tool/plugin.rs:31-46`, `src/managed_process.rs:406-423`.

## Sink: Tool Program / `task` job delegation (scheduler job surface)

- **Final effect owner**: `ToolProgramExecutor` for Tool Programs and `SubagentJobExecutor` for subagents, both under the `JobScheduler`; the `tool_program` and `task` tools are the callers.
- **Checkout locator**: the Tool Program's workspace root is taken from the parent execution context's `cwd` (`src/tool/tool_program.rs:416-421`) and re-resolved to a `workspace_id` (`src/tool/tool_program.rs:422-425`). The `task` tool's durable mutating runs receive a managed isolated worktree; read-only runs inherit the parent workspace (`src/tool/task.rs:1268`).
- **Authority path**: the Tool Program is bound to a **frozen runtime Broker catalog** — the requested tool set must equal the frozen set exactly (`src/tool/tool_program.rs:475-484`), the workspace path policy fingerprint must be current (`src/tool/tool_program.rs:426-442`), and the palette is restricted to contract effect classes `ReadOnly` or `ReadValidate` (`src/tool/program_manifest.rs:97-107`). Subagent jobs run under the scheduler's admission permit.
- **Lifetime (incl. detach/descendant question)**: **The Tool Program can outlive the request by design**: `execution_mode: "background"` returns a handle immediately and delivers a terminal notification later (`src/tool/tool_program.rs:188-195`, `src/tool/tool_program.rs:340-344`), and the program executes as a durable scheduler job. The interpreter is native and in-process, so the *program itself* spawns no process; but the tools it calls may (`src/tool/program_manifest.rs:97-107` restricts by *contract effect class*, and a tool's declared effect class is metadata, not a containment proof).
- **Reachable callers**: tool `tool_program` (`src/tool/tool_program.rs:151-153`), category `ToolCategory::ReadOnly` (`src/tool/tool_program.rs:206-208`), contract `DirectOnly` + `ReadOnly` (`src/tool/tool_program.rs:217-222`); tool `task` (`src/tool/task.rs:1259-1261`), category `Mutating` (`src/tool/task.rs:1390-1392`).
- **Existing coordination (and its limits)**: frozen contract snapshot, path-policy fingerprint, background-mode session requirement (`src/tool/tool_program.rs:403-412`), and scheduler admission. **Limits**: `JobKind::ToolProgram` carries **no** exclusivity key (`crates/codegg-core/src/jobs/mod.rs:795-802`); `JobKind::Subagent` likewise carries none (`crates/codegg-core/src/jobs/mod.rs:713-722`).
- **Adversarial bypass example**: a tool whose `contract().effect_class` is declared `ReadOnly` but whose implementation writes (or spawns a writer) is admitted into the Tool Program palette by `src/tool/program_manifest.rs:97-107` and is then invoked by a **background** Tool Program that outlives the request. The mismatch is that the *program* is metadata-read-only while the *called tool* is trusted on its declared effect class, not on a containment proof.
- **Preliminary disposition**: **denied-process** for the *background/delegating* surface (a durable job that outlives the request, with no exclusivity key). The native interpreter in foreground mode, restricted to a contract-validated read-only palette, is **read-proven** subject to the metadata caveat above. C001 work package B states the requirement directly: "distinguish a readonly tool category from a server that can write."
- **Evidence**: `src/tool/tool_program.rs:151-153`, `src/tool/tool_program.rs:188-195`, `src/tool/tool_program.rs:206-222`, `src/tool/tool_program.rs:340-344`, `src/tool/tool_program.rs:403-425`, `src/tool/tool_program.rs:426-442`, `src/tool/tool_program.rs:475-484`, `src/tool/program_manifest.rs:97-107`, `src/tool/task.rs:1259-1261`, `src/tool/task.rs:1268`, `src/tool/task.rs:1390-1392`, `crates/codegg-core/src/jobs/mod.rs:713-722`, `crates/codegg-core/src/jobs/mod.rs:795-802`.

## Descendant containment verdict

**Plain answer: descendant-tree quiescence is NOT proven for any sink on Unix (Linux/macOS). Only direct-child exit, or a process-group signal that a `setsid` descendant escapes, is available.**

- **`ManagedProcessService` family (bash, terminal, test/build/lint/format jobs, Python, plugin process, hook adapter, formatter, native git dispatch, human shell): NO.** The child is a session leader (`setsid`, `src/managed_process.rs:1760-1772`) and cleanup is a process-group `SIGTERM`/`SIGKILL` (`src/managed_process.rs:1795-1806`, `src/managed_process.rs:1813-1853`). The source states the escape explicitly: "the group kill covers processes that stayed in the session, but a descendant that called `setsid` escapes it and can keep the pipe open indefinitely" (`src/managed_process.rs:1666-1669`). `kill_on_drop(true)` is direct-child only (`src/managed_process.rs:777`). No cgroup, no `/proc` descendant walk, no pidfd tree tracking exists in this tree.
- **Same family on Windows: PARTIALLY YES for lifetime, NO for write authority.** `ManagedProcess` assigns the child to a Job Object created with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`src/managed_process.rs:799-800`, `src/managed_process/windows.rs:849-869`, flag at `src/managed_process/windows.rs:856`) and terminates via `job.terminate(1)` (`src/managed_process.rs:1860-1868`), which is a genuine tree kill. This bounds *process lifetime* on Windows only; it does not restrict what the tree may write, and it does not apply to any sink below that does not go through `ManagedProcessService`.
- **PTY family: NO.** Session leader via `setsid()` + `TIOCSCTTY` (`src/interactive_process.rs:1283-1297`); cleanup is a process-group `SIGTERM`→`SIGKILL` (`src/interactive_process.rs:891`, `:894`, `:955-966`) — the same escaping-group mechanism, with no Windows job object on this path.
- **Local MCP child: NO.** `child.kill()` and `start_kill()` are direct-child operations (`src/mcp/local.rs:516`, `src/mcp/local.rs:727`); no session, group, or descendant tracking in that file.
- **LSP server child: NO.** `child.start_kill()` (`crates/egglsp/src/runtime.rs:263`) and `process.child.kill()` (`crates/egglsp/src/launch.rs:210`) are direct-child operations; no group or job object.
- **Tool Program / `task` delegation: NO for the delegated job's process lifetime** (the durable job may run long after the request); the native interpreter spawns no process at all, so the question does not apply to it.

**Important distinction that must not be collapsed:** a process-group signal or a `setsid` observation is **not** filesystem containment. Conversely, the Landlock backend *is* filesystem containment that survives descendant escape: `restrict_self()` is applied in the helper before exec (`src/security/sandbox/landlock.rs:117-125`) and the resulting domain is inherited by every descendant, so a `setsid` descendant that outlives the group kill is still denied writes outside the granted roots. The same Landlock guarantee is **not** available to the sinks that never request a sandbox — the hook adapter, the formatter, the process plugin, the native git dispatch, the `terminal` tool, the PTY, the MCP child, and the LSP child all launch with `SandboxRequest::Disabled` or no sandbox mechanism at all. Landlock's own recorded limits include "open file descriptors inherited before restriction remain usable" (`src/security/sandbox/landlock.rs:34`), and the guarantee contract lists `require_job_containment` as a distinct dimension (`src/security/sandbox/guarantee.rs:67-68`).

## Coverage gaps

1. **No sink in this audit can prove checkout-scoped writer lifetime on Unix.** The process-group mechanism is escaped by `setsid` (`src/managed_process.rs:1666-1669`), and the two persistent sinks (MCP, LSP) do not even attempt a group signal. Any restricted shared-checkout profile must therefore deny these surfaces rather than fence them, consistent with C005 work package C and the C005 stop criterion ("Full process-tree containment is NOT required to pass restricted v1 if every unqualified process surface is correctly denied before use").
2. **Scheduler exclusivity does not cover the writers it most needs to cover.** `JobKind::Shell`, `JobKind::ManagedProcess`, `JobKind::Test`, `JobKind::Lint`, `JobKind::Python` and `JobKind::ToolProgram` all carry an empty exclusivity-key set (`crates/codegg-core/src/jobs/mod.rs:731-802`), while `exclusive:workspace-mutation` and `exclusive:worktree-mutation` are distinct bare names that never conflict (`src/scheduler/admission.rs:201-211`). The admission controller also holds no notion of *which checkout* a key refers to, so even `workspace-mutation` is daemon-global rather than per-checkout.
3. **The `JobExecutionContext.workspace_root` contract is not honoured by the executor.** The context field documents "Executors must use this instead of consulting process-global CWD" (`src/scheduler/executor.rs:150-152`), but `ManagedArgvExecutor` uses the durable payload's `cwd` instead (`src/scheduler/executors.rs:321-326`). The payload cwd is trusted because the submitter wrote it; the executor does not re-check it against the lease's workspace root.
4. **The daemon-cwd guard does not cover the directories where the worst offenders live.** `scripts/check_daemon_cwd_usage.py` scans only `src/tool`, `src/scheduler`, `src/core` plus five named files (`scripts/check_daemon_cwd_usage.py:55-66`). The following process-global `std::env::current_dir()` reads are therefore outside the guard: `src/hooks/mod.rs:117`, `src/plugin/runtime/process.rs:100`, `src/python_script/tool.rs:70`, `src/python_script/executor.rs:530`, `src/python_script/executor.rs:550`, `src/shell/rtk.rs:1044`. The hook adapter and the process-plugin runtime are the two that actually place a writer process.
5. **Two sinks have no checkout locator at all.** The local MCP child sets no `current_dir` and therefore inherits the daemon's launch directory; the hook adapter uses the daemon's `current_dir()` because `HookContext` carries no workspace root (`src/hooks/mod.rs:55-62`).
6. **Tool-metadata vs. effect mismatch is live in at least one place.** `tool_program` is `ToolCategory::ReadOnly` (`src/tool/tool_program.rs:206-208`) yet submits a durable job that can run in background mode past the request (`src/tool/tool_program.rs:340-344`, `src/tool/tool_program.rs:403-412`). The palette gate uses the tool's *declared* `ToolEffectClass` (`src/tool/program_manifest.rs:97-107`), which is metadata, not a containment proof — exactly the distinction C001 work package B requires.
7. **The `terminal` tool and the `native git dispatch` path carry neither a sandbox nor an execution authorization** (`src/tool/terminal.rs:283-291`, `src/tool/bash/process.rs:678-682`), so a `git` hook or a formatter-invoked binary has full filesystem authority with no per-request record.
8. **Preexisting persistent processes are not detected by anything in this tree.** Nothing in the scheduler admission path inspects whether an MCP child, LSP server or PTY is already running against the target checkout before a reservation (C005 work package E). UNPROVEN: I did not find a preflight that enumerates live persistent writers per checkout; the guards cited in `scripts/verify.sh quick` are call-site and shape checks, not liveness checks.

## Cross-cutting notes

- **A single owner, many callers.** `ManagedProcessService` is the one production owner for every finite process writer (`src/managed_process.rs:802`); the `bash` tool, `terminal`, the plugin runtime, the hook adapter, the formatter, the Python executor and the human shell are all callers. The persistent writers — the PTY service, the MCP `LocalClient` and the `egglsp` runtime — are three *separate* owners with three *separate* kill mechanisms, and none of the three is a group or tree kill.
- **Everything persistent is configured, not model-directed.** The MCP child comes from operator config (`src/mcp/mod.rs:746-763`), the LSP server from LSP config (`crates/egglsp/src/client.rs:650`), the plugin from the plugin manifest and trust class (`src/plugin/policy.rs:68-85`), the hook from hook config (`src/hooks/mod.rs:97-110`). That lowers the *model-reachability* risk but does not lower the *writer* risk: a configured child is a long-lived, unsandboxed writer rooted at the checkout, and C005 §C requires exactly this distinction to be made rather than assumed away.
- **Model-originated vs. human-originated.** The human `!` shell is the only sink with a coherent principal-and-sandbox path (`src/core/daemon_human_shell.rs:141-180`). Everything model-originated reaches a process through either `ManagedProcessService` (no authorization by default: `src/managed_process.rs:421`) or a raw `Command::new` (MCP, LSP, PTY — no scheduler admission, no exclusivity key, no sandbox). The `tool_program` and `task` tools are model-originated job-delegation surfaces that deliberately outlive the request.
- **The `exclusive:` key vocabulary is the closest thing to a write-coordination primitive in the tree, and it is not checkout-scoped.** It is a daemon-global, bare-name mutex with a one-slot meaning, applied to only two job kinds (`crates/codegg-core/src/jobs/mod.rs:723-746`). A restricted-profile writer permit will have to be a *different* primitive: per-checkout, and held across the writer's true lifetime rather than its process exit.
- **UNPROVEN items.** (a) Whether any non-`ManagedProcess` sink can be retro-fenced with a Windows job object — I found no job-object assignment outside `src/managed_process.rs` / `src/managed_process/windows.rs`. (b) Whether the scheduler's daemon-generation restart logic reaps or re-admits already-running MCP/LSP/PTY children — I did not trace `src/job_recovery.rs` or `src/core/daemon_construct.rs` far enough to establish it, so I am not claiming it either way. (c) Whether `src/shell/rtk.rs` (the human-shell projection/redirect layer) spawns anything beyond `ManagedProcessService` — I did not audit it beyond its `current_dir` uses.
