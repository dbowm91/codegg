## Cross-cutting notes

- **ToolBroker is the only production tool-call boundary for every native sink in this cluster — the broker's final dispatch is a direct in-process call, not a scheduler route.** `src/tool/broker.rs:886` and `src/tool/broker.rs:892` call `tool.execute_structured(attempt_input, Some(exec_ctx))` on the registry's tool object. The broker's module doc lists "6. Route selection (inline native or scheduler-owned)" (`src/tool/broker.rs:12`), but the executed code path performs no route selection: the tool runs inline in the calling process. **The C001 matrix must state this plainly: for the native file and git sinks, "through ToolBroker" and "in the caller's process" are the same thing — there is no scheduler-owned serialization step between the broker and the effect.**
- **No native file or git sink in this cluster takes the per-repository lock.** `WorkspaceLockTable::acquire_repository` exists (`crates/codegg-core/src/workspace_services.rs:219`) and is used by exactly three callers in scope: the LSP preview apply (`src/lsp/mutation.rs:403`), the worktree service (`crates/codegg-core/src/worktree_service.rs:899`, `:950`, `:977`, `:1070`), and the batch executor (`src/agent/tool_batch.rs:1438`). `write`, `edit`, `replace`, `apply_patch`, `formatter`, `git` (typed/raw/network/recovery), `commit`, and the HTTP file route take no lock at all.
- **The batch coordination is batch-local and eligibility-gated, and it is much narrower than "the tool batch is serialized."** A batch is checkpoint-eligible only if EVERY tool in it is restorable (`write`|`edit`|`replace`|`multiedit`|`apply_patch`) or affirmatively read-only. `src/agent/tool_batch.rs:1388-1391`, `crates/codegg-core/src/snapshot/affected_paths.rs:35`. A batch containing `git`, `bash`, `terminal`, `formatter`, or `task` is therefore NOT eligible and takes NO repository lease. Separately, the in-batch serialization (`checkpoint_serialize` → `effective_max = 1`) is triggered only when the batch's own affected paths overlap each other — `has_overlapping_paths(raw_len, normalized.len())`. `src/agent/tool_batch.rs:1414-1418`, `crates/codegg-core/src/snapshot/affected_paths.rs:267`. And the lease itself is best-effort: on timeout the batch "proceeds without checkpoint authority". `src/agent/tool_batch.rs:1435-1448`. **What it does NOT cover: writers in different sessions, writers in different turns, the HTTP file route, any batch containing a non-restorable tool, and any writer that is not a native file tool.**
- **The lock table is per-process, in-memory, and per-workspace-bundle; it does not survive a daemon restart.** `crates/codegg-core/src/workspace_services.rs:204-207` (a `DashMap` inside a plain struct), `crates/codegg-core/src/workspace_services.rs:420` (a fresh table per workspace bundle), `crates/codegg-core/src/workspace_services.rs:243-245` (entries dropped on eviction). It is also keyed on the **canonical repository root**, not on a file path — `crates/codegg-core/src/workspace_services.rs:220-228` — so even where it is used it is a coarse per-repo mutex, not a per-file one.
- **Two disjoint lock tables exist in the same daemon.** The agent loop's table comes from the workspace service lease (`src/agent/turn_runtime.rs:329`), while the `WorktreeService` gets its own freshly constructed table (`src/core/daemon_construct.rs:223`, `src/core/runtime_deps.rs:261`, `:310`, `:374`). The `WorktreeService` is therefore not mutually excluded with the agent's writers.
- **The `git` tool's `workdir` is model-supplied and unvalidated — this is the sharpest containment hole in the cluster.** `src/tool/git.rs:342-345` reads `input["workdir"]` and falls back to the registry root; the only check is existence. `src/tool/git.rs:350-355`. That path then becomes the repo root via `resolve_repo_root`, which requires only "exists, is a directory, has `.git`". `src/git_mutations.rs:343-364`. The structured *read* path uses the registry-supplied `self.workdir` instead. `src/tool/git.rs:116`. And `extract_path_from_tool_call` has no `"git"` arm, so the `workdir` never reaches the path-scoped permission check. `src/agent/tool_inspect.rs:83-92`. **The C001 matrix must state that the `git` tool's checkout locator is model-controlled and that this is a containment gap independent of writer overlap.**
- **`replace` and `commit` are path-invisible to the permission layer.** `extract_path_from_tool_call` matches `"read" | "write" | "edit" | "glob" | "grep" | "list"` (`src/agent/tool_inspect.rs:86`) and `"apply_patch"` (`src/agent/tool_inspect.rs:89`) — no `"replace"`, no `"commit"`, no `"git"`. `src/agent/tool_inspect.rs:83-92`. `replace` writes a file whose path the operator never sees in the approval surface.
- **The typed `git` mutation path is not scope-narrowed by the permission layer.** The scope for the `git` tool is derived from `subcommand`/`command` (`src/permission/mod.rs:636`), but the typed path uses the `mutation` field (`src/tool/git.rs:358-362`), so a typed mutation produces no narrow scope and falls back to broad rows.
- **Metadata that claims read-only but can write:** `git_read`/`git_query` are labelled `ReadOnly` and are genuinely read-only (allow-listed operations, `deny_unknown_fields`, no `workdir` field). `src/tool/git_read.rs:64`, `src/tool/git_read.rs:67`, `src/tool/git_read.rs:119`, `src/tool/git_read.rs:411`. By contrast, the risk classifier used for batch eligibility is a **name/argument-string** classifier: `classify_tool_risk` classifies `cargo build` and `make install` as `ToolRisk::Read` even though both write to disk. `src/tool/risk.rs:154`, `src/tool/risk.rs:158`. That mislabel does not make them eligible for the batch (they are not in the restorable set, `crates/codegg-core/src/snapshot/affected_paths.rs:35`), but it means the "affirmatively read-only" arm of the eligibility test rests on string matching, not on a capability contract.
- **`apply_patch` publishes no `FileChanged` event**, while `write` (`src/tool/write.rs:126`), `edit` (`src/tool/edit.rs:204`), `replace` (`src/tool/replace.rs:280`), and the LSP apply (`src/lsp/mutation.rs:509`) do. The batch's file-change-driven state detection therefore cannot observe an `apply_patch` write. `src/agent/snapshot_capture.rs:190-208`.
- **The `lsp_preview_apply` path is the reference fence** in this cluster — digest check, per-file `original_hash` check, dirty-buffer gate, repository lock, atomic write, rollback, post-state verification. `src/lsp/mutation.rs:397-401`, `src/lsp/mutation.rs:431-436`, `src/lsp/mutation.rs:360-369`, `src/lsp/mutation.rs:403`, `src/lsp/mutation.rs:442-459`. The native file sinks have none of these except containment.
- **A latent `unrestricted` flag exists on every native file tool and is a containment escape if ever enabled.** `WriteTool`, `EditTool`, `ReplaceTool`, and `ApplyPatchTool` each carry an `unrestricted: bool`; when true, the path is validated only by a symlink check on the parent, with no root containment. `src/tool/write.rs:12`, `src/tool/write.rs:77`, `src/tool/write.rs:83-98`, `src/tool/edit.rs:18`, `src/tool/edit.rs:124-133`, `src/tool/replace.rs:18`, `src/tool/replace.rs:124-133`, `src/tool/apply_patch.rs:25`, `src/tool/apply_patch.rs:185-189`, `src/tool/apply_patch.rs:379-392`. In the audited tree the flag defaults to `false` in every one of the four (`src/tool/write.rs:19`, `src/tool/edit.rs:26`, `src/tool/replace.rs:26`, `src/tool/apply_patch.rs:33`) and the only public setter that sets it true belongs to `ListTool` (`src/tool/list.rs:38-40`), a read-only tool. **The C001 matrix should record this as latent, not live: the escape is real in the code but unreachable in the current production registration path** (`src/tool/mod.rs:685`, `src/tool/mod.rs:692`, `src/tool/mod.rs:875`, `src/tool/mod.rs:888` — all use `with_allowed_root`, which resets the flag to false at `src/tool/write.rs:25`, `src/tool/edit.rs:33`, `src/tool/edit.rs:44`).
- **Reachable-caller summary for the matrix:** the native sinks are reached through ToolBroker only, from the daemon turn runtime (`src/agent/turn_runtime.rs:899`), the CLI (`src/exec.rs:173`, `src/main.rs:2947`), the delegated child worker (`src/agent/worker.rs:1509`), the tool-program executor (`src/scheduler/tool_program_executor.rs:164`), and a TUI diagnostics path (`src/tui/commands/diagnostics.rs:221`). The HTTP server reaches no native tool — its only tool route lists tools (`src/server/routes/tool.rs:27`) — but it has its own independent file write/delete sink (`src/server/routes/file.rs:238`, `src/server/routes/file.rs:276`).
